## Fix: Rider Online Toggle & Order Notification Badge

### Root Cause Analysis

#### 1. Rider ไม่สามารถกด Online ได้ (SignalR WebSocket ล้มเหลว)
- **ปัญหา**: Nginx ใช้ `proxy_pass http://host.docker.internal:5000/hubs/` แบบ hardcode
- `host.docker.internal` resolves เป็น IPv6 address (`fdc4:f303:9324::254`) ก่อน IPv4
- .NET Backend ฟังเฉพาะ IPv4 (`127.0.0.1:5000`) ไม่ได้ฟัง IPv6
- สำหรับ HTTP request ธรรมดา Nginx retry upstream อื่นได้ → ผ่าน (นั่นทำไม negotiate 200 OK)
- แต่สำหรับ **WebSocket upgrade** Nginx ไม่ retry → connection ล้มเหลวทันที → SignalR ต่อไม่ได้ → goOnline() throw error

#### 2. Rider badge บน nav bar ไม่แสดง
- `MainShell` เป็น `StatelessWidget` ไม่ได้ watch provider ใดเลย
- ไม่มีการแสดง badge เมื่อมี dispatch offer เข้ามา

### Changes

#### `rider_app/nginx/default.conf` [MODIFIED]
```nginx
# เพิ่ม:
resolver 127.0.0.11 ipv4=on valid=30s;  # บังคับ IPv4-only DNS resolution
set $backend "http://host.docker.internal:5000";  # ใช้ variable ให้ nginx re-resolve ทุก request

# เปลี่ยน proxy_pass จาก hardcode URL → ใช้ $backend variable
# เพิ่ม headers ครบสำหรับ WebSocket: X-Real-IP, X-Forwarded-For
# เพิ่ม proxy_connect_timeout 10s, proxy_send_timeout 86400s
```

- แปลง `MainShell` จาก `StatelessWidget` → `ConsumerWidget`

- แสดง `Badge(backgroundColor: Colors.red, label: '!')` บนไอคอน "งานส่ง" เมื่อมี offer เข้ามา

## Phase 9 & 9.5: System Stress Testing, Concurrency Hardening & Chaos Resilience

เราได้รันการทดสอบและปรับปรุงระบบในส่วนของ Stress Test (Phase 9) และ Concurrency Hardening (Phase 9.5) รวมถึงการยิงโหลดผสมผสานกะทันหันร่วมกับ Chaos Injection (Stage 5) รายละเอียดดังนี้:

### 1. Database Concurrency Control Hardening (Phase 9.5)

#### ปัญหาที่พบ (Root Cause Analysis)
* จากการทดสอบ **Stage 2.5 (Database Lock Contention Test)** พบคอขวดเรื่อง Data Collision: ออเดอร์ถูกแย่งกดยอมรับพร้อมกันแต่ระบบยอมให้ผ่านหมด (สำเร็จถึง 5,217 ครั้ง แทนที่จะสำเร็จเพียงครั้งเดียวตามกฎของ State Machine)
* เนื่องจาก EF Core และ Npgsql ไม่ได้ทำการอัปเดตหรือตรวจสอบคอลัมน์ `RowVersion` ประเภท `bytea` บน PostgreSQL โดยอัตโนมัติหากไม่มีการสร้าง Database Triggers ส่งผลให้ Optimistic Concurrency ถูกข้ามไปโดยไม่ตั้งใจ (Bypassed Concurrency Check)

#### การแก้ไข (Changes)
* **`BackendApi/Data/ApplicationDbContext.cs` [MODIFIED]**
  - เปลี่ยนโครงสร้างการตรวจสอบ Concurrency จากเดิมที่อ้างอิง `RowVersion` แบบธรรมดา ไปใช้ความสามารถของ PostgreSQL System Column ที่ชื่อว่า **`xmin`** (Transaction ID ของการอัปเดตแถวล่าสุดของแถวนั้นๆ)
  - เรียกใช้เมธอด `.UseXminAsConcurrencyToken()` บน Entities ทุกตัวที่สืบทอดมาจาก `BaseEntity<>` ทำให้เกิดการทำ Optimistic Concurrency Verification โดยอัตโนมัติโดยไม่ต้องทำ Database Migration
* **`BackendApi/Features/DispatchManagement/StateMachineService.cs` [MODIFIED]**
  - ล้อมการทำงานคำสั่ง `SaveChangesAsync()` ด้วยบล็อก `try-catch` เพื่อจับข้อผิดพลาด `DbUpdateConcurrencyException`
  - หากตรวจพบการชนกันของคำขอ (Data Collision) จะตีตกเป็น `400 BadRequest` อย่างถูกต้อง แทนการปล่อยหลุดเป็น `500 Server Error`
