มาตรฐานความปลอดภัยระบบ AI Agent อ้างอิงตาม OWASP (OWASP Top 10 for LLMs)

วัตถุประสงค์: เอกสารฉบับนี้จัดทำขึ้นเพื่อให้ AI Agent อ่าน ทำความเข้าใจ และใช้เป็นแนวทาง (Guideline) ในการตรวจสอบ วิเคราะห์ และปรับปรุงสถาปัตยกรรม โค้ด และการทำงานของโปรเจกต์ให้มีความปลอดภัยสูงสุด

📋 คำสั่งสำหรับ AI Agent (System Directive)
เมื่อคุณ (AI Agent) อ่านเอกสารนี้ ให้คุณตรวจสอบโปรเจกต์ที่ได้รับมอบหมาย โดยเปรียบเทียบกับรายการความเสี่ยงทั้ง 10 ข้อด้านล่าง หากพบความเสี่ยง ให้เสนอแนะวิธีแก้ไข (Mitigation) ทันที

🛡️ OWASP Top 10 สำหรับ AI และ LLM

LLM01: Prompt Injections (การฉีดคำสั่งแปลกปลอม)
คำอธิบาย: การที่ผู้ใช้ป้อนข้อมูลที่หลอกลวงหรือปรับเปลี่ยนพฤติกรรมของ AI Agent ให้ทำในสิ่งที่ไม่ได้รับอนุญาต หรือข้ามผ่านระบบความปลอดภัย (Jailbreak)
ผลกระทบ: AI อาจแสดงข้อมูลที่บิดเบือน, ทำการโจมตีระบบอื่นต่อ, หรือให้ข้อมูลที่เป็นความลับ
แนวทางปรับปรุง (Mitigation):
- แยกข้อมูลที่ผู้ใช้ป้อนออกจากคำสั่งระบบ (System Prompts) ให้ชัดเจน
- จำกัดสิทธิ์ของ AI Agent (Principle of Least Privilege)
- ใช้ระบบตรวจสอบ (Filter) ข้อมูลขาเข้าและขาออก

LLM02: Insecure Output Handling (การจัดการผลลัพธ์ที่ไม่ปลอดภัย)
คำอธิบาย: การนำผลลัพธ์ที่สร้างจาก AI ไปใช้งานต่อโดยตรง (เช่น รันคำสั่ง, แสดงผลบนหน้าเว็บ) โดยไม่มีการคัดกรอง (Sanitization)
ผลกระทบ: เสี่ยงต่อการเกิด XSS (Cross-Site Scripting), CSRF, หรือ Remote Code Execution (RCE)
แนวทางปรับปรุง (Mitigation):
- ถือว่าผลลัพธ์จาก AI เป็นข้อมูลที่ไม่น่าเชื่อถือ (Untrusted Data) เสมอ
- ทำการ Encode หรือ Sanitize ผลลัพธ์ก่อนนำไปแสดงผลหรือประมวลผลต่อ

LLM03: Training Data Poisoning (การวางยาข้อมูลสำหรับฝึกสอน)
คำอธิบาย: การที่ข้อมูลที่นำมาใช้ฝึกหรือปรับจูน (Fine-tuning) โมเดล ถูกดัดแปลง แทรกรหัสร้าย หรือข้อมูลเท็จ
แนวทางปรับปรุง (Mitigation):
- ตรวจสอบแหล่งที่มาของข้อมูล (Data Provenance)
- ทำความสะอาดและตรวจสอบข้อมูลก่อนนำเข้าสู่กระบวนการ Training หรือ RAG (Retrieval-Augmented Generation)

LLM04: Model Denial of Service (การโจมตีเพื่อให้โมเดลหยุดให้บริการ)
คำอธิบาย: การป้อนคำถามหรือข้อมูลที่ทำให้ AI ต้องใช้ทรัพยากรในการประมวลผลสูงมากจนระบบล่ม
แนวทางปรับปรุง (Mitigation):
- จำกัดจำนวนคำ (Rate Limiting) และความยาวของ Token ทั้งขาเข้าและขาออก (Max Tokens)
- ตรวจสอบการใช้งานทรัพยากร (Resource Monitoring) อย่างเข้มงวด

LLM05: Supply Chain Vulnerabilities (ช่องโหว่จากห่วงโซ่อุปทาน)
คำอธิบาย: การใช้โมเดลสำเร็จรูป, ปลั๊กอิน, หรือไลบรารีจากบุคคลที่สาม (Third-party) ที่มีช่องโหว่หรือถูกฝังมัลแวร์
แนวทางปรับปรุง (Mitigation):
- ใช้โมเดลและปลั๊กอินจากแหล่งที่เชื่อถือได้เท่านั้น
- สแกนหาช่องโหว่ใน Dependency (เช่น ใช้เครื่องมือ SBOM)
- ทำ Sandboxing สภาพแวดล้อมที่รัน AI

LLM06: Sensitive Information Disclosure (การเปิดเผยข้อมูลที่ละเอียดอ่อน)
คำอธิบาย: AI Agent เผลอเปิดเผยข้อมูลความลับ ข้อมูลส่วนบุคคล (PII) หรือข้อมูลทางธุรกิจที่อยู่ใน Training Data หรือฐานข้อมูล
แนวทางปรับปรุง (Mitigation):
- ทำ Data Masking หรือ Anonymization ข้อมูลก่อนให้ AI ประมวลผล
- จำกัดสิทธิ์การเข้าถึงข้อมูลของ AI (RAG access control)
- กำหนด System Prompt ไม่ให้ AI ตอบคำถามที่เป็นความลับ

LLM07: Insecure Plugin Design (การออกแบบปลั๊กอินที่ไม่ปลอดภัย)
คำอธิบาย: ปลั๊กอินหรือ API ที่ AI Agent เรียกใช้ ขาดการตรวจสอบสิทธิ์หรือการควบคุมการเข้าถึงที่รัดกุม
แนวทางปรับปรุง (Mitigation):
- ใช้การยืนยันตัวตนแบบเข้มงวด (เช่น OAuth2) สำหรับทุกปลั๊กอิน
- กำหนดพารามิเตอร์ของ API ให้ชัดเจนและทำการ Validate ข้อมูลทุกครั้งที่ AI ส่งไปเรียกใช้

LLM08: Excessive Agency (การให้สิทธิ์ AI Agent มากเกินไป) 🔴 สำคัญมากสำหรับ AI Agent
คำอธิบาย: การอนุญาตให้ AI Agent ดำเนินการที่ส่งผลกระทบสูง (เช่น ลบไฟล์, ส่งอีเมล, ทำธุรกรรม) โดยไม่มีการตรวจสอบจากมนุษย์ (Human-in-the-loop) หรือให้สิทธิ์เกินความจำเป็น
แนวทางปรับปรุง (Mitigation):
- ให้สิทธิ์ AI เท่าที่จำเป็นสำหรับการทำงาน (Least Privilege)
- กำหนดให้ต้องมีการอนุมัติจากมนุษย์ (Human Approval) ก่อนทำ Action ที่มีความเสี่ยงสูง
- จำกัดขอบเขตการทำงานของ Function Calling

LLM09: Overreliance (การพึ่งพา AI มากเกินไป)
คำอธิบาย: การเชื่อถือผลลัพธ์จาก AI โดยไม่มีการตรวจสอบ ซึ่งอาจนำไปสู่ข้อผิดพลาดจากอาการหลอน (Hallucinations) หรือโค้ดที่มีช่องโหว่
แนวทางปรับปรุง (Mitigation):
- ออกแบบระบบให้มีการทำ Cross-validation
- สื่อสารให้ผู้ใช้ทราบเสมอว่าข้อมูลนี้สร้างโดย AI และอาจมีความผิดพลาด
- กรณี AI เขียนโค้ด ต้องมีกระบวนการ Review จากนักพัฒนา หรือ Automated Testing

LLM10: Model Theft (การขโมยโมเดล)
คำอธิบาย: ผู้ไม่หวังดีเข้าถึงและขโมยโมเดล (Weights, Parameters) ของเราไปใช้
แนวทางปรับปรุง (Mitigation):
- จำกัดการเข้าถึง API
- ใช้ระบบ Monitoring ตรวจจับพฤติกรรมการเรียก API ที่ผิดปกติ (เพื่อป้องกัน Shadowing/Model Extraction)

🔍 เช็คลิสต์สำหรับการตรวจสอบโปรเจกต์ (Action Items for AI Agent)
เมื่อคุณวิเคราะห์โค้ดหรือระบบ โปรดประเมินและรายงานตามหัวข้อต่อไปนี้:
- [ ] Input Pipeline: มีการทำ Sanitization ก่อนส่งให้ LLM หรือไม่? (อ้างอิง LLM01)
- [ ] Output Pipeline: มีการทำ Escape/Encode ก่อนนำผลลัพธ์ของฉันไปใช้งานหรือไม่? (อ้างอิง LLM02)
- [ ] Permissions & Function Calling: ฉัน (AI Agent) มีสิทธิ์ในการเข้าถึงระบบมากเกินความจำเป็นหรือไม่? มีระบบ Human-in-the-loop สำหรับคำสั่งอันตรายไหม? (อ้างอิง LLM07, LLM08)
- [ ] Data Privacy: ข้อมูลที่ส่งเข้ามาหาฉันมีการลบข้อมูล PII ออกไปแล้วหรือยัง? (อ้างอิง LLM06)
- [ ] Resource Limits: ระบบมีการตั้ง Timeout และ Max Tokens เพื่อป้องกัน DoS หรือไม่? (อ้างอิง LLM04)
