### 🚨 ระบบล่มระหว่างการทำ Load Test ที่ระดับ 500 Riders (Thundering Herd Bottlenecks)

**ปัญหาที่พบ (The Breaking Points):**
1. **ThreadPool Starvation:**
   - **สาเหตุ:** การยิง GPS ผ่าน `SignalR` เข้าสู่ `StackExchange.Redis` ด้วยคำสั่ง `await` ต่อเนื่อง (4-6 queries ต่อ 1 GPS update) ทำให้เมื่อมี 500 connections ยิงพร้อมกัน เกิด ThreadPool ขาดแคลน (Starvation) เนื่องจาก .NET จะค่อยๆ สร้าง Thread ใหม่ขึ้นมา (1 thread ต่อ 500ms) ส่งผลให้ Tasks รอคิวทำงานนานเกิน 15 วินาที ทำให้ฝั่ง Client ถูกตัดการเชื่อมต่อด้วย Error `Connection closed with an error`
   - **การแก้ไข:** ปรับแก้ใน `Program.cs` โดยการตั้งค่า `ThreadPool.SetMinThreads(1000, 1000)` เพื่อเตรียมพร้อมรับมือกับ Thundering Herd ของ Asynchronous I/O burst

2. **RabbitMQ Synchronous TCP Blocking:**
   - **สาเหตุ:** `GpsRabbitMqPublisher` เดิมใช้ `lock` คู่กับ `BasicPublish` ทับซ้อนกับ SignalR thread pool ทำให้เกิดปัญหา Socket buffer เต็มเมื่อโหลดเข้ามารัวๆ และบล็อก thread ทั้งหมด
   - **การแก้ไข:** รีแฟกเตอร์ให้ใช้ `System.Threading.Channels.Channel<TrackPoint>` เปลี่ยนเป็น Asynchronous Publisher Worker (Fire-and-Forget ลง Memory Channel แบบไม่บล็อก Thread)

3. **PostgreSQL Connection Exhaustion (Too many clients):**
   - **สาเหตุ:** เมื่อ 500 Riders เชื่อมต่อ (Connect/Reconnect) เมธอด `OnConnectedAsync` จะดึงค่าจาก DB ผ่าน EntityFramework ทำให้เกิดการใช้ Database Connection Pool 500 ตัวพร้อมกัน แต่ฐานข้อมูล PostgreSQL ใน `docker-compose.yml` คอนฟิกค่าดีฟอลต์ไว้ที่ `max_connections=100` ส่งผลให้ Connection เต็มและพ่น Error ออกมา `53300: sorry, too many clients already`
   - **การแก้ไข:** แก้ไข `docker-compose.yml` โดยเพิ่มพาเนลใน command เป็น `-c max_connections=1000`

**ผลลัพธ์หลังแก้ไขสถาปัตยกรรม (Final Benchmark):**
- ทดสอบรันสคริปต์ **500 Riders** ยิง GPS ต่อเนื่อง 60 วินาที
- 🎯 **ผลลัพธ์ที่ได้:** ทะลุเป้า **0 Errors, 0 Disconnects** สามารถประมวลผล GPS พุ่งถึง **20,000+ points/minute** (เฉลี่ย 330 points/sec) โดยที่ ThreadPool ทำงานได้อย่างราบรื่นและคอนเนกชันไม่ดรอปเลย

## 5. การปรับปรุงสถาปัตยกรรมระดับสูง (Advanced Architectural Refactoring)
เพื่อยกระดับความสมบูรณ์แบบและการทนทานต่อโหลดปริมาณมหาศาล (Load Resilience) เราได้ทำ Refactoring สถาปัตยกรรมระบบ 3 ส่วนสำคัญ:

### 🛠️ ส่วนที่ 1: ระบบทาบแผ่นดินแบบไร้การขัดจังหวะ (Asynchronous Map Matching)
- **ปัญหาเดิม:** การเรียกใช้งาน OSRM HTTP API ในการทาบพิกัดบนผิวถนน (Snap-to-Road) บล็อกการสตรีมพิกัดในจุดรับข้อมูล (Hot Path) ก่อให้เกิด Thread Pool Exhaustion
- **การแก้ไข:** 
  - สร้างหน่วยประมวลผลฉากหลังตัวใหม่ **`OsrmSnapWorker` (BackgroundService)** แยกต่างหากเพื่อดูดพิกัดดิบจาก RabbitMQ `gps_snap_queue` ไป Snap นอกโปรเซสหลัก
  - ปรับปรุง `GpsRabbitMqPublisher` ให้รองรับการส่งพิกัด Snap แบบไร้การขัดจังหวะ (Non-blocking Memory Channel `_snapChannelQueue`)
  - อัปเดตพิกัดถนนที่สวยงามลง Redis Cache Hash `riders:snapped_gps:{riderId}` พร้อมกระจายพิกัดสู่หน้าแผงควบคุมแอดมินแบบเรียลไทม์ด้วย SignalR Event `RiderLocationSnapped` (มี `isSnapped: true` และ Throttling 1.0 วินาทีเพื่อปกป้องเซิร์ฟเวอร์ OSRM)

### 🛠️ ส่วนที่ 2: ดึงข้อมูลพิกัดจากความจำสำรองโดยตรง (Redis-first Location API)
- **ปัญหาเดิม:** เมื่อผู้ใช้งานรีเฟรชหน้าแผงควบคุม (F5) ข้อมูลตำแหน่งเริ่มต้นถูกดึงมาจาก PostgreSQL ซึ่งเก็บพิกัดเก่าตอน Rider เปลี่ยนสถานะ ส่งผลให้รถบนหน้าจอกลานดินมีอาการวาร์ปกระโดดถอยหลัง
- **การแก้ไข:**
  - สร้าง API Endpoint สำหรับหน้าบ้านตัวใหม่ **`GET /api/v1/rider-locations` (`RiderLocationController.cs`)** สำหรับ Admin/Dispatcher
  - ใช้ Redis `SCAN` และกลไก **Pipelining/Batching (`CreateBatch` / `HashGetAllAsync`)** ดึงพิกัดทั้งหมดและข้อมูลถนนที่ถูก snap จาก Redis Presence ใน O(1) TCP Roundtrip เท่านั้น
  - ปรับปรุงส่วนหน้าแผงควบคุมแอดมิน Angular (`map.component.ts` และ `dashboard.component.ts`) ให้เรียกใช้งานพิกัดเริ่มต้นแบบ Redis-first เสมอ และติดตั้งฟังก์ชัน Glide/Animate ทรานส์พอร์ตรถไปยังตำแหน่งถนนที่สมบูรณ์แบบเมื่อตรวจพบ Event `RiderLocationSnapped`

### 🛠️ ส่วนที่ 3: บันทึกสถานะการออนไลน์แบบถาวร (Durable State Changes via RabbitMQ)
- **ปัญหาเดิม:** หน่วยจัดการการเชื่อมต่อ `RiderPresenceManager` ใช้การรันเมธอดทรานซิชันสถานะในหน่วยความจำ RAM (`_ = Task.Run(...)`) หากระบบ Backend ดับกะทันหัน ข้อมูลสถานะการทำงานของไรเดอร์ (Connect/Disconnect/Job State) จะหล่นหาย
- **การแก้ไข:**
  - กำจัดชุดโค้ด `Task.Run` ออกทั้งหมด แล้วแทนที่ด้วยการยิง Event **`RiderStateChangedIntegrationEvent`** เข้าสู่ RabbitMQ เพื่อรับประกันความคงอยู่ของข้อมูล (Durability)

## 7. เฟส 5: Data-Driven Observability (Testing Dashboard)

ในการดำเนินงานล่าสุด เราได้บูรณาการระบบ **Testing Dashboard** ร่วมกับความสามารถในการดักจับ ประมวลผล และวิเคราะห์ผลลัพธ์ข้อมูลการทดสอบแบบเรียลไทม์ (Real-time Load Metric Extraction) ซึ่งเปลี่ยนสแต็กทดสอบให้เป็นแพลตฟอร์มสังเกตการณ์ประสิทธิภาพระบบอย่างสมบูรณ์:

*   **ขยายขีดความสามารถฝั่ง Backend & Worker**:
    *   **LogParserService**: พัฒนาระบบดักจับข้อมูล Metrics เชิงตัวเลขผ่าน Regex (เช่น `RPS`, `Latency`, `Error Rate`) สกัดออกจาก stdout ของ `resilience-stress.js` ขณะรันใน Docker Sandbox
    *   **Data Persistence**: จัดเก็บ Metric Object ลงใน Artifact JSON ไฟล์ และทำการ Push ผลลัพธ์เข้า Redis Queue/History
    *   **Sandbox Policy**: เพิ่ม `load-breaking-point`, `load-massive-batch`, และ `load-chaos-reconnect` ลงใน `sandbox-policy.json` เพื่อปลดล็อคการรัน Extreme Tests แบบใหม่จากหน้าบ้าน
*   **ยกระดับระบบหน้าบ้าน UI (Chart.js + Angular)**:
    *   **MetricsChartComponent**: สร้าง Dashboard วิเคราะห์ผลลัพธ์ประสิทธิภาพในรูปแบบกราฟิก:
        *   **Gauge Chart (เข็มมาตรวัด)**: แสดงความเร็วการส่งข้อมูล (RPS) เรียลไทม์พร้อมการเปลี่ยนระดับสีเตือนเมื่อเข้าใกล้จุดแตกหัก (เช่น 5,000 RPS)
        *   **Line Chart**: กราฟพล็อตเปรียบเทียบแนวโน้ม (Trend) ความสัมพันธ์ระหว่าง Requests/sec และ Latency อย่างชัดเจน
    *   **OverallOverviewComponent**: บูรณาการชุดกราฟิกเข้ากับหน้าแสดงผลรวม โดยสตรีมข้อมูลดิบจาก `latestLoadSession.metrics` อย่างไหลลื่น
*   **ปรับแต่งประสิทธิภาพ Real-time Streaming & Terminal Highlighting**:
    *   **Socket.IO Log Batching (Throttling)**: แก้ไขปัญหาเบราว์เซอร์ค้าง (UI Freezes) ในช่วงโหลดทดสอบ 5,000+ RPS โดยใช้ระบบ Buffer บีบอัดและปล่อย Event `log` ออกเป็นชุดในจังหวะทุกๆ **500ms**
    *   **Terminal Color Highlighting**: พัฒนา Regex ดักจับ Keyword สำคัญใน `LiveTerminalComponent` เช่น `Error`, `Timeout`, `Passed`, `0.00%`, `BREAKING POINT` และแปลงเป็น ANSI Color codes ทันทีก่อนนำส่ง xterm
*   **การเชื่อมโยงระบบ (Automation & Architecture Documentation)**:
    *   ปรับปรุงสคริปต์ **`start-local.ps1`** ให้ตรวจสอบสถานะการทำงานของคอนเทนเนอร์ `test-dashboard-redis` และสร้างขึ้นใหม่อัตโนมัติหากพบว่าปิดตัวลง ป้องกันปัญหาระบบ Pub/Sub ล่มทำงานไม่ได้
    *   อัปเดตไฟล์ **`README.md`** แสดงแผนผังลำดับขั้นตอนการส่งข้อมูลจาก Sandbox -> API -> Socket.IO -> UI

## 8. การแก้ไขปัญหาการรันเทส Backend ผ่าน Docker Sandbox (Hermetic Integration Testing)

เราได้แก้ไขปัญหาที่ทำให้ไม่สามารถรันชุดการทดสอบ Backend (C# Integration Tests) จากหน้า Testing Dashboard ที่รันอยู่ภายใต้ Ephemeral Docker Sandbox:

*   **สาเหตุของปัญหา**: ชุดการทดสอบ `TelemetryControllerTests` เดิมพึ่งพา Redis บน `localhost:6379` ของ Host เครื่องภายนอก เมื่อรันชุดทดสอบผ่าน Sandbox Container จึงไม่สามารถเข้าถึง Redis ตัวนอกได้ และทำให้เกิดการพ่นข้อผิดพลาด `InternalServerError (500)` กลับมา
*   **การดำเนินการแก้ไข**:
    *   นำไลบรารี **`Testcontainers.Redis`** เข้ามาใช้ในชุดการทดสอบ `BackendApi.IntegrationTests`
    *   ปรับปรุงคลาส **`DeliveryWebApplicationFactory.cs`** ให้สร้างและสปินคอนเทนเนอร์ `RedisContainer` (จากอิมเมจ `redis:7-alpine`) แบบแยกเดี่ยว (Isolated) ขึ้นมาทำงานคู่กับ PostgreSQL และ RabbitMQ Testcontainers โดยอัตโนมัติ
    *   ส่งค่า Connection String ของ Redis จาก Testcontainer เข้าไปทับสิทธิ์ตัวแปรระบบ (`ConnectionStrings:Redis` และ `Redis`) ใน config หลัก
*   **ผลลัพธ์**: ตอนนี้ชุดการทดสอบ Integration Tests ทั้งหมด **ผ่านการรันสำเร็จสมบูรณ์แบบ 100% (Passed: 43 / 43 Tests!)** ทั้งการรันบนโฮสต์ปกติและการรันแบบ Hermetic Sandbox ภายใน Docker Dashboard
